# Is Dantrix ready to freeze for v1.0?

**Decision: yes. The maintainer chose the freeze on 2026-10-17, the three
blockers below were resolved in v1.0.0 itself, the first frozen release.**

An analysis, written before any decision was made. The question is not "is the
project finished" but "is the **public surface** ready to promise never to change
in a breaking way", because that is what v1.0 means under Semantic Versioning.

> Written at v0.8.11, reviewed at v1.0.3, resolved at v1.0.0. The counts in
> the "evidence" section describe the range they name (v0.7.1 to v0.8.11); they
> are history, not a claim about the current release.

## What "frozen" actually commits us to

After v1.0.0, all of this becomes a promise:

1. **49 configuration keys** keep their names, types, defaults and meaning.
   The count is verified against the registry, not copied from prose: 48 are
   printed by `--print-config` and `add_header` is printed only when set.
   Renaming `max_conns_per_ip` or changing what `header_timeout` counts as
   requires a major version. The count fell from 50 to 49 when
   `edge_triggered` was removed (see below).
2. **46 CLI flags** keep their spelling and semantics. Verified by counting the
   `getopt_long` table and confirming each one appears in `--help`.
3. **HTTP behaviour** keeps its observable shape: status codes, headers, framing,
   which requests are rejected, and what the error bodies say.
4. **The status endpoint** keeps its JSON field names, since monitoring systems
   parse them.
5. **The access log** keeps its format: `common`, `combined`, and the JSON field
   names (`ts`, `peer`, `method`, `target`, `protocol`, `status`, `bytes`,
   `referer`, `user_agent`), one object per line.
6. **Semantics, not just syntax.** Changing `header_timeout` from a deadline to a
   gap (or back) is a breaking change even though the key is unchanged.

That is a long promise for a project that changed its behaviour repeatedly: the
15 releases from v0.7.1 to v0.8.11 recorded **72 changes** (29 added, 26 fixed,
6 changed, 5 verified), and six of them are the kind that would be breaking
after v1.0. The six are listed below; the rest were additions and fixes that
leave the surface compatible.

## The evidence: the six breaking-ish changes in that range

| Release | Breaking-ish change |
|---|---|
| v0.7.1 | `header_timeout` silently became a **deadline** instead of a gap |
| v0.7.3 | The open-file cache arrived, changing staleness semantics for files |
| v0.8.0 | The status JSON gained a `descriptors` object |
| v0.8.1 | `max_conns_per_ip` arrived, plus `connlimit_slots` |
| v0.8.2 | `seccomp` arrived |
| v0.8.10 | `add_header` went from **accepted-and-ignored to actually working**, and gained validation that can refuse a config that previously started |

The v0.8.10 entry is the important one: a key that did nothing became a key that
does something, and a configuration that used to start can now be refused. That
is exactly the kind of change that is easy to make before v1.0 and impossible
after.

## The blockers, and how each was resolved

### 1. `edge_triggered` was accepted and ignored -- **removed**

The configuration accepted `edge_triggered = true` and start-up printed a
warning that it had no effect. That is the same shape as `add_header` before
v0.8.10: a key that appears to configure something and does not.

**Resolution (v1.0.0): the key was deleted.** Setting it is now an unknown-key
error (exit code 2, verified), `--print-config` no longer lists it, and the
documentation no longer offers a mode that does not exist. Implementing
edge-triggered would mean auditing every read and write path for the "drain
until `EAGAIN`" discipline, where a mistake is a hang rather than a slowdown;
that work was not done, so the option was removed instead of promised. See
[`adr/0002-level-triggered-default.md`](adr/0002-level-triggered-default.md).

### 2. The HTTP surface had a documented gap: multi-range -- **permanent**

Multi-range requests (`Range: bytes=0-10,20-30`) are ignored and answered with a
full `200`. That is a **deliberate** choice, justified by the overlapping-range
attack gap.

**Resolution (v1.0.0): frozen as a permanent deviation.** RFC 9110 permits a
server to ignore `Range`; it does not require honouring it. The README now says
the behaviour is permanent and will not change without a major version, so a
client author can rely on it rather than hope.

### 3. `log_format = json` was documented but rejected -- **implemented**

The registry listed `json` as a valid value, the documentation mentioned it, and
setting it failed at parse time with exit code 2. That was the honest failure
mode, but a frozen surface should not advertise a value that cannot be used.

**Resolution (v1.0.0): implemented.** `log_format = json` now emits one JSON
object per line with the field names listed above. Verified by parsing every
emitted line with `json.loads`, including a target containing a quote and a
backslash and a `User-Agent` containing a quote: the JSON escaper writes `\"`,
`\\` and `\u00XX`, not the `\xHH` escape the common format uses, because `\xHH`
is not valid JSON.

### 4. The `header_timeout` change was recent -- **exercised**

It became a deadline in v0.8.3. Before the freeze it was exercised by the
one-hour soak (3,601 s, 700,671 requests, RSS slope +1.64 MiB/h against a
4.00 MiB/h budget, descriptors flat at 217) and by the 24-hour fuzz campaign
(2,174,927,120 executions, zero crashes). Those were the two long runs this
document was waiting for.

## What is genuinely ready

These have been stable for many releases and have tests that would catch a
regression:

| Area | Why it is safe to freeze |
|---|---|
| The static file path (`sendfile`, `ETag`, `Range`, `HEAD`, MIME) | Unchanged since v0.3 except for bug fixes; 8 response paths all covered by tests |
| The strict parser rules | Rejections have only been *added* since v0.2; no rule was ever loosened |
| Multi-worker with `SO_REUSEPORT` | Stable since v0.5 |
| The signal interface (TERM/QUIT/HUP/USR1/USR2) | Stable since v0.6, documented per signal |
| Build-time hardening | Stable, verified by reading the ELF |

## Options that were considered

### Option A: freeze v1.0.0 with the blockers open
**Cost:** a dead key, a documented value that does not work, an unexercised
timeout semantic, and an undocumented RFC deviation frozen in place. Any fix
afterwards needs v2.0.
**Verdict:** dishonest.

### Option B: fix the blockers, then freeze -- **chosen**
**Work:** remove `edge_triggered`; implement `log_format = json`; declare the
multi-range deviation permanent; let the timeout semantics run in the long tests.
**Verdict:** done in v1.0.0.

### Option C: never freeze; stay at v0.x
**Gain:** complete freedom to change anything.
**Cost:** a project that never claims stability is a project nobody builds on.
**Verdict:** rejected by the maintainer.

## What the maintainer decided

1. **`edge_triggered`**: removed.
2. **`log_format = json`**: implemented.
3. **Multi-range**: permanent deviation, documented as such.
4. **The freeze**: yes, v1.0.0.
