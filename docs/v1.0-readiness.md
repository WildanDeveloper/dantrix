# Is Dantrix ready to freeze for v1.0?

An analysis, written before any decision is made. The question is not "is the
project finished" but "is the **public surface** ready to promise never to change
in a breaking way", because that is what v1.0 means under Semantic Versioning.

> Written at v0.8.11 and reviewed at v0.8.20. The counts below describe the range
> they name (v0.7.1 to v0.8.11); they are history, not a claim about the current
> release. The four blockers in this document are still open at v0.8.18 -- the
> releases since then changed tests and documentation, not the public surface.

## What "frozen" actually commits us to

After v1.0.0, all of this becomes a promise:

1. **50 configuration keys** keep their names, types, defaults and meaning.
   The count is verified against the registry, not copied from prose: 49 are
   printed by `--print-config` and `add_header` is printed only when set.
   Renaming `max_conns_per_ip` or changing what `header_timeout` counts as
   requires a major version.
2. **46 CLI flags** keep their spelling and semantics. Verified by counting the
   `getopt_long` table and confirming each one appears in `--help`.
3. **HTTP behaviour** keeps its observable shape: status codes, headers, framing,
   which requests are rejected, and what the error bodies say.
4. **The status endpoint** keeps its JSON field names, since monitoring systems
   parse them.
5. **Semantics, not just syntax.** Changing `header_timeout` from a deadline to a
   gap (or back) is a breaking change even though the key is unchanged.

That is a long promise for a project that changed its behaviour repeatedly: the
15 releases from v0.7.1 to v0.8.11 recorded **72 changes** (29 added, 26 fixed,
6 changed, 5 verified), and six of them are the kind that would be breaking
after v1.0. The six are listed below; the rest were additions and fixes that
leave the surface compatible.

## The evidence: the six breaking-ish changes in that range

| Release | Breaking-ish change |
|---|---|
| v0.7.1 | `header_timeout` silently became a **deadline** instead of a gap |
| v0.7.3 | The open-file cache arrived, changing staleness semantics for files |
| v0.8.0 | The status JSON gained a `descriptors` object |
| v0.8.1 | `max_conns_per_ip` arrived, plus `connlimit_slots` |
| v0.8.2 | `seccomp` arrived |
| v0.8.10 | `add_header` went from **accepted-and-ignored to actually working**, and gained validation that can refuse a config that previously started |

The v0.8.10 entry is the important one: a key that did nothing became a key that
does something, and a configuration that used to start can now be refused. That
is exactly the kind of change that is easy to make before v1.0 and impossible
after.

**The surface is still moving.** Twelve releases produced at least six changes a
user could notice. Freezing now would either freeze something still unsettled, or
force a v2.0 shortly after v1.0 for a change that should have been free.

## Unfinished business that blocks a freeze

### 1. `edge_triggered` is accepted and ignored

The configuration accepts `edge_triggered = true`, and start-up prints
*"edge_triggered is not implemented; the server runs level-triggered and this key
has no effect"*. The message used to name v0.7 as the release that would
implement it — a version that shipped nine releases ago — so the schedule was
removed rather than corrected to another version that might also slip. This is
the same shape as `add_header` before v0.8.10: a key that appears to configure
something and does not.

**Cannot freeze with a dead key.** Either implement it, remove it, or document it
as reserved. Removing it is the honest option: the README already explains why
level-triggered is the default, and an unimplemented switch is a trap for the
operator who sets it and believes it took effect.

### 2. The HTTP surface has a documented, deliberate gap

Multi-range requests (`Range: bytes=0-10,20-30`) are ignored and answered with a
full `200`. That is a **deliberate** choice, documented and justified, but it is a
deviation from RFC 9110 that a user could reasonably expect to change. Freezing it
means promising the deviation forever.

### 3. `log_format = json` is documented but rejected

The registry lists `json` as a valid value, the documentation mentions it, and
setting it fails at parse time with exit code 2 (`unknown log format 'json'`,
verified). That is the honest failure mode -- it refuses rather than silently
downgrading to `combined` -- but a frozen surface should not advertise a value
that cannot be used. Either implement it or stop documenting it as an option.

### 4. The `header_timeout` change is recent

It became a deadline in v0.8.3, seven releases ago. It is the right behaviour and
the documentation now matches it, but it has had little real-world use. Freezing
a timeout semantic that has not been exercised outside this machine is a risk.

## What is genuinely ready

These have been stable for many releases and have tests that would catch a
regression:

| Area | Why it is safe to freeze |
|---|---|
| The static file path (`sendfile`, `ETag`, `Range`, `HEAD`, MIME) | Unchanged since v0.3 except for bug fixes; 8 response paths all covered by tests |
| The strict parser rules | Rejections have only been *added* since v0.2; no rule was ever loosened |
| Multi-worker with `SO_REUSEPORT` | Stable since v0.5 |
| The signal interface (TERM/QUIT/HUP/USR1/USR2) | Stable since v0.6, documented per signal |
| Build-time hardening | Stable, verified by reading the ELF |

## Options, with the honest trade-off

### Option A: freeze v1.0.0 now
**Gain:** a finished-looking project; a clear line for a reader.
**Cost:** we would freeze a dead key, a documented value that does not work, an
unexercised timeout semantic, and a deliberate RFC deviation. Any fix afterwards
needs v2.0.
**Verdict:** dishonest. It would present a surface as settled that is not.

### Option B: fix the blockers, then freeze
**Work:** remove or implement `edge_triggered`; decide on `log_format = json`
(reject the key at parse time, or implement it); decide whether the multi-range
deviation is permanent (document it as such, permanently); let the timeout
semantics run in the soak test for an hour first.
**Cost:** roughly one session of work, plus a soak run.
**Verdict:** this is what "ready" should mean.

### Option C: never freeze; stay at v0.x
**Gain:** complete freedom to change anything.
**Cost:** a project that never claims stability is a project nobody builds on.
**Verdict:** acceptable for a learning project, but it should then be stated
plainly in the README rather than implied by a v1.0.0 section that never lands.

## Recommendation

**Option B, and not yet.** The two long runs are still pending, and both are
evidence a freeze should rest on:

1. the 24-hour fuzz campaign (running; 469M executions so far, zero crashes);
2. the 1-hour soak, which cannot run until the fuzzers release the CPU.

Until those finish, "the surface is stable" is an assertion without the two
measurements that would support it. The blockers above are small and concrete;
they are the right work for the next session, not a v1.0.0 tag now.

## What I would ask the maintainer to decide

These are judgement calls, not technical ones, and they are the maintainer's:

1. **`edge_triggered`**: remove it, or implement `EPOLLET`? Implementing it means
   auditing every read path for the "drain until EAGAIN" discipline that
   edge-triggered requires; getting it wrong is a hang, not a slowdown.
2. **`log_format = json`**: implement it, or delete the value from the docs and
   reject the key?
3. **Multi-range**: keep the deviation permanently, or implement it?
4. **The freeze itself**: is v1.0.0 wanted as a *finished portfolio piece*, or is
   the project more valuable as a living v0.x that keeps changing?
